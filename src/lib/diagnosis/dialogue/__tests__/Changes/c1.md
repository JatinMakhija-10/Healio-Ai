## Part I — Remediation Spec (Build This First)
*Addendum to v3.2 Architecture Report | Prepared for Engineering Sign-off*

This spec turns the review findings into two concrete, buildable pieces: (1) a deterministic red-flag override gate that runs *before* any Bayesian reasoning, and (2) a proposal to replace the custom DVT α-stacking with the validated Wells' Criteria. Both are designed to slot into the existing pipeline (`healthPersona.ts` → `MCMCEngine.ts` → `ddi.ts` → `chat/route.ts`) without a rewrite.

---

### I.1 Red-Flag Override Gate

**Problem:** Currently, red flags appear to be handled as weighted inputs to the Bayesian engine — one signal among many. For a defined set of presentations, that's the wrong model. A patient reporting crushing chest pain radiating to the arm should never wait on a posterior calculation; they should hit a hard, deterministic stop.

**Design principle:** This gate runs *first*, outside the Bayesian pipeline, on raw parsed symptom text. It is a simple rule table, not a model — auditable, testable, and immune to LLM prompt drift.

```typescript
// redFlagGate.ts — runs BEFORE MCMCEngine, on every turn

type RedFlagRule = {
  id: string;
  patterns: RegExp[];          // matched against parsed symptom text
  excludeIfNegated: boolean;   // true = skip if negation detected upstream
  action: "EMERGENCY_STOP" | "URGENT_ESCALATION";
  message: string;             // fixed, clinician-reviewed copy — never LLM-generated
};

const RED_FLAG_RULES: RedFlagRule[] = [
  {
    id: "chest_pain_cardiac",
    patterns: [/chest (pain|pressure|tightness)/i, /pain.*(arm|jaw|back).*chest/i],
    excludeIfNegated: true,
    action: "EMERGENCY_STOP",
    message: "This combination of symptoms needs immediate in-person emergency evaluation. Please call your local emergency number or go to the nearest ER now — this is not something to assess further here."
  },
  {
    id: "stroke_fast",
    patterns: [/(sudden|one[- ]?sided).*(weakness|numbness|droop)/i, /slurred speech/i, /sudden.*vision loss/i],
    excludeIfNegated: true,
    action: "EMERGENCY_STOP",
    message: "These can be signs of a stroke, where minutes matter. Please call emergency services immediately."
  },
  {
    id: "suicidal_ideation",
    patterns: [/(want|going|plan) to (die|kill myself|end (it|my life))/i],
    excludeIfNegated: false, // never skip, even if phrased tentatively
    action: "EMERGENCY_STOP",
    message: "[Route to crisis resources, not clinical model — separate handling required]"
  },
  {
    id: "severe_breathing_difficulty",
    patterns: [/(can'?t|unable to) (breathe|catch (my|his|her) breath)/i, /gasping/i],
    excludeIfNegated: true,
    action: "EMERGENCY_STOP",
    message: "Difficulty breathing like this needs emergency care right away. Please call emergency services."
  },
  {
    id: "suspected_dvt_pe",
    patterns: [/sudden.*(shortness of breath|chest pain).*swelling/i],
    excludeIfNegated: true,
    action: "URGENT_ESCALATION",
    message: "This combination raises concern for a blood clot. Please seek same-day in-person medical evaluation — don't wait for this to resolve on its own."
  },
  // ... additional rules reviewed and signed off by a licensed clinician before merge
];

function checkRedFlags(parsedSymptomText: string, negationFlags: Set<string>): RedFlagResult | null {
  for (const rule of RED_FLAG_RULES) {
    const matched = rule.patterns.some(p => p.test(parsedSymptomText));
    if (matched && !(rule.excludeIfNegated && negationFlags.has(rule.id))) {
      return { rule, message: rule.message };
    }
  }
  return null;
}

// In chat/route.ts, BEFORE calling MCMCEngine or the LLM:
const redFlag = checkRedFlags(parsedInput, negationFlags);
if (redFlag) {
  return respondWithFixedSafetyMessage(redFlag.message); // bypasses LLM entirely
}
```

**Key properties:**
- **Fixed, non-generative output.** The message is not LLM-authored — it's clinician-approved copy pulled verbatim. This removes the risk of the model softening or hedging an emergency message under conversational pressure.
- **Runs pre-persona.** A red flag fires the same way whether or not a Health Persona has been built, so this doesn't depend on the reliability of upstream parsing.
- **Negation-aware, but fails safe.** For ambiguous or high-stakes rules (self-harm), `excludeIfNegated` is `false` — the system escalates even on a hedge rather than risk a false negative.
- **Every rule requires clinician sign-off before merge** — this table should live under change control like a formulary, not standard PR review.

### I.2 Replacing Custom DVT Multipliers with Wells' Criteria

**Problem:** Section 3 of the original report multiplies three risk-factor odds ratios together (obesity ×2.5, sedentary ×1.8, hormonal contraceptive ×2.0 → capped at ×5.0) to produce a DVT posterior. This double-counts correlated risk factors and has no cohort validation behind the specific multiplier values or the cap.

**Proposal:** For DVT/PE — and any condition with an existing validated clinical decision rule — replace the custom α-stack with the rule itself, computed deterministically from the same persona data already being parsed.

```typescript
// wellsScore.ts — deterministic, validated, replaces custom DVT multiplier stack

interface WellsInput {
  activeCancer: boolean;
  paralysisOrRecentCast: boolean;
  recentlyBedriddenOrSurgery: boolean; // >3 days bedridden, or major surgery <12wks
  localizedTendernessDeepVeins: boolean;
  entireLegSwollen: boolean;
  calfSwellingOver3cm: boolean;        // vs asymptomatic leg
  pittingEdemaAffectedLegOnly: boolean;
  collateralSuperficialVeins: boolean;
  previousDVT: boolean;
  alternativeDiagnosisAsLikely: boolean; // clinician/LLM-flagged, subtracts
}

function computeWellsScore(i: WellsInput): { score: number; risk: "low" | "moderate" | "high" } {
  let score = 0;
  if (i.activeCancer) score += 1;
  if (i.paralysisOrRecentCast) score += 1;
  if (i.recentlyBedriddenOrSurgery) score += 1;
  if (i.localizedTendernessDeepVeins) score += 1;
  if (i.entireLegSwollen) score += 1;
  if (i.calfSwellingOver3cm) score += 1;
  if (i.pittingEdemaAffectedLegOnly) score += 1;
  if (i.collateralSuperficialVeins) score += 1;
  if (i.previousDVT) score += 1;
  if (i.alternativeDiagnosisAsLikely) score -= 2;

  const risk = score >= 3 ? "high" : score >= 1 ? "moderate" : "low";
  return { score, risk };
}
```

**How this changes the pipeline:**
- `PersonaEngine.ts` already extracts most Wells inputs (BMI/mobility → recent surgery/bedridden proxy, family/personal history → previous DVT) — minimal new parsing needed.
- Output is a **validated risk tier** (low/moderate/high, mapped to published post-test probabilities: ~5%, ~17%, ~53% respectively in the original Wells cohort), not a bespoke percentage the system invented.
- The LLM's role shrinks to **narrating a validated tier**, not generating or influencing the number — closing the "89% confidence" calibration gap from the original review.
- The custom Bayesian MCMC layer is preserved for conditions **without** an established decision rule, but should be clearly labeled internally (and ideally to the patient) as a heuristic estimate rather than a validated score.

**Other conditions with existing rules worth the same treatment**, in priority order given what's already in the covariate table:
| Condition in current table | Validated rule to substitute |
|---|---|
| DVT/PE | Wells' Criteria (above), PERC for low-risk PE rule-out |
| Pneumonia severity | CURB-65 |
| Stroke risk (AFib) | CHA₂DS₂-VASc |
| Strep pharyngitis | Centor / McIsaac criteria |
| Sepsis screening | qSOFA |

### I.3 Suggested Build Order

1. **Red-flag gate** — highest safety leverage, smallest engineering lift, no dependency on the Bayesian layer. Ship first.
2. **Post-generation contraindication scan** — regex/keyword check of the LLM's *final output* against the patient's allergy + contraindication list before it's shown to the user, independent of pre-prompt filtering. Cheap insurance against prompt non-compliance.
3. **Wells' Criteria substitution** for DVT — proof of concept for the "validated rule over custom multiplier" pattern before extending to CURB-65 / CHA₂DS₂-VASc / Centor.
4. **Negation-aware comorbidity parsing** — audit `parseConditionFlags` against a test set of "no history of X" / "mother has X" phrasings before trusting it to gate medication safety.
5. **Fail-closed default** — confirm and, if needed, enforce that any exception in `MCMCEngine.ts` or `ddi.ts` blocks the response rather than silently passing through unfiltered.
6. **Versioning/change-control** on `COVARIATE_RULES` and the red-flag table — treat as clinical content requiring sign-off, not routine code.

Items 1–2 are safety-critical and clinician-reviewable independent of the rest of the roadmap; I'd decouple them from any larger MCMC refactor timeline.

## Part II — Full Analysis & A–Z Scalability Blueprint
*Full Analysis, Criticism, and the Scalable Architecture Behind Part I*

---

### II.1 Analysis — What the System Does

Healio.AI builds a **Health Persona** from onboarding data (age, sex, BMI, medications, conditions, family history, lifestyle) and uses it in four ways:

1. Shifts disease **prior probabilities** before a Bayesian (Beta-distribution) posterior is computed, via hand-picked α multipliers across 12 rule groups.
2. Filters candidate remedies against active medications/conditions/pregnancy (**ddi.ts**).
3. Computes derived risk scores — BMI category, polypharmacy tier, a custom "Clinical Frailty Index."
4. Injects the structured profile into the LLM's system prompt so responses are personalized and use non-presumptive question phrasing.

This is a reasonable idea in principle — pretest probability *should* depend on patient covariates, that's standard Bayesian clinical reasoning. The problems are all in the *implementation*, not the concept.

---

### II.2 Issues & Criticism

### 2.1 The multiplier table is hand-written and closed-world
Only 12 rule groups exist, covering a handful of comorbidities, a handful of medication classes, and no surgical history at all. Any patient whose relevant risk factor isn't one of the ~30 hardcoded conditions gets treated as if that factor doesn't exist. This isn't a bug in the code — it's a structural ceiling: **a hardcoded `if/switch` table cannot scale to real-world clinical variety**, where there are tens of thousands of relevant diagnoses (ICD-11 has ~55,000 codes), tens of thousands of drugs, and thousands of distinct procedures.

### 2.2 Naive multiplication double-counts correlated risk
The DVT example multiplies obesity (×2.5) × sedentary lifestyle (×1.8) × hormonal contraceptive (×2.0) = ×9.0, then silently caps to ×5.0. Obesity and sedentary behavior are not independent causal pathways to DVT — they overlap heavily. Multiplying their marginal relative risks together overstates the joint effect, and the ad hoc cap hides the error rather than fixing it.

### 2.3 No sourcing, versioning, or confidence attached to any multiplier
The report presents ranges like "×1.8–×2.5" with no citation, no confidence interval, no indication of which studies they're derived from, and no version history. A clinician auditing this system today cannot tell whether these numbers are literature-derived, expert guesses, or arbitrary.

### 2.4 Allergy and drug matching appear to be exact-string, not class-based
Real allergy safety requires **cross-reactivity** reasoning (e.g., penicillin allergy → caution with cephalosporins, ~1–2% cross-reaction rate), and real drug interaction checking requires **class-based** reasoning (any anticoagulant × any antiplatelet, not just named pairs). A fixed list of named substances will miss anything not explicitly enumerated.

### 2.5 No surgical/procedural history modeling at all
Past surgeries meaningfully change risk (splenectomy → infection risk from encapsulated organisms; bariatric surgery → altered drug absorption/dosing; recent joint replacement → VTE risk window) and current architecture has no field, parser, or rule group for this category.

### 2.6 Point-probability output without calibration
"89% confidence" is presented to a layperson without any stated calibration study behind it. Confidently wrong is worse than honestly uncertain in a clinical tool.

### 2.7 No deterministic red-flag layer, no fail-closed behavior, no change-control process
(Covered in the prior remediation spec — included here for completeness of the A–Z picture.)

---

### II.3 The Scalable Solution — Core Idea

**Replace hand-written rule tables with a data-driven knowledge layer built on standard medical coding systems, plus a mathematically sound aggregation model.** The code should never again contain a hardcoded list of diseases or drugs — it should contain a *generic engine* that looks up structured data. This is the same shift every mature clinical software system has made: from bespoke logic to **ontology + rules-as-data**.

### 3.1 Adopt standard coding systems instead of free-text/regex matching

| Domain | Standard to adopt | Why |
|---|---|---|
| Diseases / conditions | **ICD-11** (or ICD-10-CM) | ~55,000+ codes, hierarchical (parent/child), globally maintained |
| Medications | **RxNorm** (ingredient-level) + **ATC classification** | Maps brand→generic→class automatically; enables class-level rules |
| Allergies | **Allergy/cross-reactivity ontology** built on RxNorm ingredient classes | Enables "any beta-lactam" not just "penicillin" |
| Procedures / surgeries | **SNOMED CT procedure hierarchy** | Standard, hierarchical, maps to downstream risk categories |
| Symptoms | **SNOMED CT clinical findings** | Same benefit — hierarchy means "chest pain" parents cover subtypes |

Once profile data is parsed into codes from these systems (instead of regex-matched free text), everything downstream — priors, DDI checks, dosing — becomes a **lookup against structured data**, not a hand-maintained if/else chain. This is the single highest-leverage architectural change: it turns a linear-growth engineering problem (add code for every new condition) into a data-loading problem (add a row to a table).

### 3.2 Replace multiplicative α-stacking with a log-additive risk model

Instead of:
```
finalAlpha = baseAlpha × riskFactor1 × riskFactor2 × riskFactor3 × ... (then cap)
```
use a **log-odds additive model**, which is how real epidemiological risk scores (e.g., logistic regression-based clinical scores) combine covariates:

```
logOdds(disease) = baseLogOdds
                  + Σ (weight_i × covariate_i)          // independent factors, additive in log space
                  + Σ (interactionWeight_jk × covariate_j × covariate_k)  // ONLY where evidence supports a true interaction
```

This fixes the double-counting problem directly: additive log-odds is the mathematically correct way to combine multiple independent risk factors (it's literally what logistic regression does), and it only adds an interaction term when there's a specific, evidenced reason two factors compound rather than just co-occur. No arbitrary cap is needed because the model doesn't blow up multiplicatively in the first place — extreme cases are naturally bounded by the logistic transform back to probability space.

### 3.3 Generalized multiplier/weight schema — "rules as data"

Every risk relationship becomes a **row in a table**, not a line of code:

```typescript
interface RiskModifier {
  id: string;                     // stable identifier
  sourceCodeSystem: "ICD11" | "RxNorm-ATC" | "SNOMED-Procedure" | "Lifestyle" | "Demographic";
  sourceCode: string;              // e.g. ICD-11 code for "Obesity Class III"
  targetCodeSystem: "ICD11";
  targetCode: string;              // e.g. ICD-11 code for "DVT"
  weightLogOdds: number;           // additive log-odds weight, NOT a multiplier
  evidenceGrade: "A" | "B" | "C" | "expert-consensus"; // GRADE-style evidence rating
  sourceCitation: string;          // DOI / PMID / guideline reference — mandatory, never blank
  lastReviewedBy: string;          // clinician sign-off identity
  lastReviewedDate: string;
  version: number;
}
```

**How you get to A–Z coverage without hand-writing 55,000 × 55,000 relationships:**
- **Don't enumerate every disease-disease pair.** Instead, define modifiers at the *category* level using the ICD/SNOMED hierarchy (e.g., "any condition under Renal Disease umbrella" → a shared modifier set for nephrotoxic drug avoidance), and let specific child codes inherit the parent's modifiers unless a more specific override exists. This is exactly how SNOMED/ICD-based clinical decision support systems scale in practice.
- **Populate the table from existing structured medical knowledge, not from scratch.** Relative-risk weights for common conditions already exist in public epidemiological literature, and drug interaction severity data already exists in maintained pharmacology databases (e.g., FDA-published label interaction data, RxNorm's own interaction mappings). Wherever such a maintained source exists, the engineering task is **integration**, not authorship — writing your own multiplier for "warfarin + aspirin" duplicates work that pharmacology-grade interaction checkers already do reliably.
- **Default weight = 0 (no effect) unless a modifier is explicitly present.** This makes "unknown" the safe default instead of silently ignoring an unlisted condition as if it were handled.
- **Every row requires evidence grade + citation + clinician sign-off before merge.** No number enters the table without a traceable source — this is the fix for issue 2.3 above.

### 3.4 Allergies at scale — cross-reactivity graph, not a list

```typescript
interface AllergyClass {
  id: string;
  rxNormIngredientClass: string;      // e.g. "beta-lactams"
  crossReactiveClasses: {
    classId: string;                  // e.g. "cephalosporins"
    crossReactivityRate: number;      // e.g. 0.01–0.02 for penicillin→cephalosporin
    recommendation: "avoid" | "caution-monitor" | "safe-with-note";
  }[];
}
```
A patient allergy is recorded against an **ingredient class**, and the DDI filter walks the cross-reactivity graph rather than matching drug names. This is how real clinical allergy-checking systems (e.g., hospital EHR allergy modules) work, and it's the only way "penicillin allergy" correctly and automatically flags amoxicillin, ampicillin, and (with appropriate caution weighting) cephalosporins without anyone hand-listing every brand name.

### 3.5 Medications at scale — leverage existing interaction databases via integration, don't reinvent

Rather than writing bespoke pairwise drug rules, the scalable path is to **integrate with an existing, maintained drug-interaction data source** (there are established open and commercial interaction databases built and maintained by pharmacology teams specifically for this purpose) and treat `ddi.ts` as an **orchestration layer**: it takes the patient's RxNorm-coded medication list, queries the interaction database for pairwise/class interactions, and applies the *severity tier* the database returns (contraindicated / major / moderate / minor) to decide suppression vs. warning-badge behavior. This is both more scalable and more clinically trustworthy than a hand-authored list, since interaction databases are continuously updated as new drugs and interactions are discovered — something a static internal table can never keep up with.

### 3.6 Past surgeries / procedures at scale

```typescript
interface ProcedureRiskProfile {
  snomedProcedureCode: string;
  procedureName: string;
  persistentRiskModifiers: RiskModifier[];  // e.g. splenectomy -> encapsulated organism infection risk (lifelong)
  timeWindowRiskModifiers: {
    modifier: RiskModifier;
    activeWindowDays: number;               // e.g. VTE risk elevated for ~90 days post major surgery
  }[];
  medicationConsiderations: string[];       // e.g. bariatric surgery -> altered oral drug absorption, avoid certain extended-release formulations
}
```
This closes the gap identified in 2.5 — surgical history becomes a first-class, structured input with the same modifier mechanism as diseases and medications, rather than being absent from the model entirely.

### 3.7 Combinatorial explosion — how to avoid needing infinite rows

You will never author a row for every possible pair of conditions. The scalable answer is a **three-tier fallback system**:

1. **Tier 1 — Specific, evidenced modifier exists** (e.g., "Obesity Class III → DVT," sourced and signed off): use it directly.
2. **Tier 2 — No specific modifier, but a parent-category modifier exists** (e.g., patient has an uncommon connective tissue disorder with no specific DVT weight, but it falls under "autoimmune/inflammatory" category which does have a general VTE-risk modifier): inherit the category-level weight, flagged internally as lower-confidence (`evidenceGrade: "category-inherited"`).
3. **Tier 3 — No modifier at all, anywhere in the hierarchy**: weight = 0, and — critically — **the system should say so explicitly to the clinician/patient** ("this condition isn't factored into the current risk estimate") rather than silently proceeding as if it had been considered. Silent gaps are far more dangerous than disclosed ones.

### 3.8 Governance pipeline — how new A–Z entries actually get added safely

```
New condition/drug/procedure identified
        ↓
Mapped to standard code (ICD-11 / RxNorm / SNOMED)  — engineering task
        ↓
Literature/database search for relative risk or interaction severity — clinical task
        ↓
Draft RiskModifier row with citation + evidence grade
        ↓
Clinician review board sign-off (versioned, logged, reversible)
        ↓
Shadow-mode deployment: new rule scores compared against old system on historical cases, no live effect
        ↓
Calibration check: do resulting probabilities match observed outcomes in test cases?
        ↓
Promote to production, version-tagged, changelog entry mandatory
```
This turns "add a new disease to the system" from an ad hoc code change into a repeatable, auditable pipeline — the same rigor a hospital formulary committee applies to adding a new drug.

### II.5 What This Buys You

- **True A–Z scalability**: adding "Ehlers-Danlos syndrome" or "post-gastric-bypass status" becomes a data-entry + sign-off task, not a code release.
- **Mathematically defensible risk combination**, closing the double-counting flaw that undermined trust in the original DVT example.
- **Auditability**: every number in the system traces to a source, a reviewer, and a version — which is what regulators and clinical safety reviewers will actually ask for.
- **Honest handling of gaps**: the system tells you what it doesn't know, rather than quietly treating unlisted conditions as irrelevant.

This is a larger lift than the red-flag gate and Wells' Criteria items from the prior remediation spec — those remain the right *first* ship, since they're safety-critical and self-contained. This blueprint is the multi-quarter foundation to build toward once those are live.
